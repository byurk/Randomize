# Randomize — Jamovi Module for Randomization-Based Inference

## Project overview
A Jamovi module and R package for teaching randomization-based inference in introductory statistics. Provides permutation tests and bootstrap CIs for means, proportions, slopes, and contingency tables.

- **Repo**: https://github.com/byurk/Randomize
- **Package name**: Randomize
- **Author**: Brian Yurk (yurk@hope.edu)

## Branches
- `main` — production code used by students
- `develop` — integration branch for new work; CI only builds `.jmo` files for PRs to `main` and for `v*` tags, so nothing on `develop` reaches students until it is merged and tagged

## Workflow for changes
1. Work on `develop` (or a feature branch off it); never commit directly to `main`.
2. After editing any `jamovi/*.yaml`, regenerate the `.h.R` files headlessly:
   `node <jmvtools-lib>/node_modules/jamovi-compiler/index.js --prepare . --home /Applications/jamovi.app`
   (`devtools::load_all()` and the tests read the `.h.R` files, so stale ones silently hide YAML changes).
3. Run `tests/test_analyses.R` and `tests/test_plot_invariants.R`; for plot changes also render `tests/visual/generate_plots.R <tag>` and look at the sheets (a byte-for-byte `cmp` of `out/<before>/*.png` vs `out/<after>/*.png` shows exactly which scenarios a change touched).
4. Build with `--build`, unzip the `.jmo` into `~/Library/Application Support/jamovi/modules/`, restart Jamovi, and check the affected analyses in the app (screenshots via the `drive-mac-app` skill). Typing into Jamovi text boxes drops characters: put the value on the clipboard and paste, then press Return and click elsewhere to commit.

## Architecture
Each analysis is an R6 class (e.g. `twomeanhtestClass`) inheriting from a jmvcore-generated base. The `.run()` method orchestrates computation, table population, and plot state setup. Plot rendering callbacks (`.permPlot()`, `.bootPlot()`, `.descplot()`, `.linplot()`) are called by the Jamovi framework.

Shared logic lives in utility files:
- `bootstrap_utils.R` — CI computation + bootstrap distribution plotting
- `perm_utils.R` — p-value computation + null distribution plotting + seed/direction helpers
- `conttab_utils.R` — contingency table data prep and display
- `descplot_utils.R` — grouped mean/median descriptive plots
- `convenience.R` — user-facing helpers for extracting plots/tables from R

## Build notes
- Rscript is at `/usr/local/bin/Rscript` (not on PATH in some shells).
- Jamovi is at `/Applications/jamovi.app`. Its bundled R is at `.../Frameworks/R.framework/Versions/4.5-arm64/Resources` (run via `R_HOME=<that> DYLD_FALLBACK_LIBRARY_PATH=<that>/lib <that>/bin/exec/R`).
- Installed module lives at `~/Library/Application Support/jamovi/modules/Randomize/`.
- **IMPORTANT**: `.omv` files cache old module code. When testing changes, always open Jamovi fresh with no `.omv` — import data from scratch. Otherwise the old code rides along with the file.
- **Plot resolution is chosen by the Jamovi client, not the module**: each analysis request carries `.ppi = trunc(72 × window.devicePixelRatio)` (client `_optionsExtras()`), and jmvcore renders the image at `width × ppi/72` pixels. On a Retina display plots are 144 ppi; on a 1× external display 72 ppi. Jamovi's zoom setting raises the device pixel ratio but does not re-run analyses, so already-rendered plots look fuzzy when zoomed until the analysis re-runs. Dragging a plot's edge in the results panel re-renders it at the new logical size (`widthScale`); the render callbacks pass `image$width` as `plot_width`, and `text_scale()` magnifies all plot text (theme text, observed-value label, caption, count labels and their cap) by width/400 (capped at 2×), so an enlarged plot is a true magnification rather than bigger bars with the same-size text.
- **Jamovi renders plots with `ragg::agg_png` at 72 ppi (400×350 px) on 1× displays**, and at that resolution ragg silently drops any text smaller than ggplot `size = 3` (≈ 8.5 pt), rotated or not. Keep every `geom_text`/`annotate` at size ≥ 3; the R-side batteries render at 144 ppi and will not show the problem. To reproduce headlessly, render with `ragg::agg_png(width = 400, height = 350, units = "px", background = "transparent", res = 72)` under Jamovi's R. The engine's rendered PNGs live under `/private/tmp/tmp*/<instance>/<NN analysis>/resources/` (path from `pgrep -fl jamovi-engine`).
- **jamovi 2.7 install hang**: `jmvtools::install()` *builds* the `.jmo` correctly (with jamovi's bundled R), but its final `jamovi --install` step hangs forever — jmvtools' x86_64 node launches jamovi under Rosetta and its arm64 server can't start. Instead, build headlessly and sideload:
  `node <jmvtools-lib>/node_modules/jamovi-compiler/index.js --build . --home /Applications/jamovi.app`, then unzip the `.jmo` into `~/Library/Application Support/jamovi/modules/`.
- Cross-platform `.jmo` builds (win/mac-intel/mac-arm) run in CI: `.github/workflows/build-modules.yml`; version tags (`v*`) attach them to a GitHub Release.

## Important notes
- The .h.R files are regenerated by `jmvtools::install()`. Edits to them will be overwritten.
- The `dplyr::select` vs `jmvcore::select` import warning is benign (we use explicit `dplyr::select()`).
- Most analyses use the `infer` package for bootstrap/permutation resampling. **Exceptions** (`twomeanhtest`, `twomeanCI`, `multimeanhtest`): Jamovi 2.7 replaces `stats::as.formula` with `jmvcore::asFormula`, which rejects any formula that calls a function outside a short allowlist, and `infer::specify(dep ~ group)` internally runs `t.test(response_variable(x) ~ explanatory_variable(x))` / `lm(...)` for numeric-response, factor-explanatory specifications. In the app those three analyses died with "Security violation: Unsafe function 'response_variable'". They now draw the same permutation / bootstrap distributions directly (`permute_diff_means()`, `bootstrap_diff_means()`, `permute_F()`, `f_stat()` in the utils). The tail of `tests/test_analyses.R` installs a replica of the sandbox and runs all 13 analyses under it; keep it last (the override is global). Headless check under Jamovi's own R: install the sideloaded module, then `options(.__jmv.original_as.formula = stats::as.formula)` and assign `jmvcore::asFormula` over `stats::as.formula` before calling the analyses.

## Known issues (pre-existing, not caused by refactor)
- **Contingency table rendering fails for large/many-level tables**: Using raw variables like `strength_training_7d` (8 levels) as rows causes ALL output to spin — contingency table, X² table, plot, and sim results. Happens regardless of column variable (even 8×2). The R computation completes in <0.2 sec; this is a Jamovi rendering issue.
  - **Testing note**: Tested extensively with debug logging in Jamovi 2.6.45 (solid). All R code paths complete successfully — `.init()`, `.run()`, `.preparePlot()`, `.permPlot()` all finish without error. The rendered PNG files exist on disk in `$TMPDIR/.../resources/` and are valid (verified by opening them). The issue is that Jamovi's frontend still shows a spinner.
  - **Suspected root cause**: The Jamovi frontend shows/hides the spinner based on a `status` field in the protobuf `AnalysisResponse` (see `jamovi.proto`). Status codes: INITED=1, RUNNING=2, COMPLETE=3, ERROR=4, RENDERING=5. The spinner CSS shows for status 1, 2, or 5, and hides only for status 3 (COMPLETE). The R engine communicates results to the Python server via nanomsg messages (`engine.py`). The nanomsg socket has a `RCVMAXSIZE` of 4MB. If the final COMPLETE message (which includes serialized results with all table data + image state) exceeds this limit, the message is silently dropped and the status never transitions to COMPLETE — the spinner persists forever even though the PNG is on disk. The 3×3 contingency table with N=12,219 may produce results (including serialized `infer` tibble state, contingency table values, etc.) that push the message close to or over this limit. This would also explain why the 8×7 case (56 cells × 5 sub-values) causes EVERYTHING to spin.
  - **Key source files**: `engine.py` (nanomsg 4MB RCVMAXSIZE on line ~181), `jamovi.proto` (AnalysisStatus enum), `resultsview-*.js` (frontend spinner logic keyed on data-status attribute), `image.R` / `analysis.R` in jmvcore (`.createImage` method).

## Plot display toggles (feature/plot-display-toggles branch)
When using Randomize as an R package for slides/assessments, `plot()` supports three display modes so students can estimate values themselves:

```r
plot(r)                     # full (Jamovi default): lines, text, shading
plot(r, show_text = FALSE)  # lines + tail shading, no text/caption
plot(r, show_lines = FALSE) # bare distribution only
```

- **Full** (default): dashed lines, text labels, captions, and tail shading (null dist)
- **No text** (`show_text = FALSE`): removes text annotations and captions; keeps dashed lines and tail shading
- **Bare** (`show_lines = FALSE`): removes everything — lines, labels, captions, and tail shading
- Jamovi module behavior is unchanged — toggles only apply when calling `plot()` from R
- Underlying utility functions (`plot_null_dist()`, `plot_boot_dist()`) also accept fine-grained params (`show_line`, `show_label`, `show_caption`, `show_tail` / `show_lines`, `show_caption`)

## Issue fixes on `develop` (2026-09-30)
Reported at https://github.com/byurk/Randomize/issues; each has a regression test.
- **#13 / #8 Model-Based Inference rebuilt** (`R/modelBased.b.R`, `jamovi/modelBased.*.yaml`): distribution is a single ComboBox (standard normal, t, chi-square, F); df boxes are enabled only for the distributions that use them (`dF2` = denominator df, F only); the Tail box and CI-multiplier section are enabled only for normal/t (chi-square and F are always right-tail); results are hidden until their checkbox is on, so a first-week student sees just Z with one checkbox. Shading is drawn by `plot_model_density()` from an explicit grid cut exactly at the observed value (the old `xlim = c(abs(obs), ...)` shaded from |Z|). Table columns `df` / `df₁` / `df₂` appear per distribution via column `visible:` rules; `results_table()` still works.
- **#12 zero-count level** (`singleprophtest.b.R`, `singlepropCI.b.R`): `infer::specify()` drops unused factor levels, so 5 heads / 0 tails looked single-level. When any level has count 0 the null / bootstrap proportions are drawn with `rbinom()` directly (same distribution as infer's draw/bootstrap; the infer path is untouched otherwise). Variables with ≠ 2 levels now get a clear `jmvcore::reject()` instead of an infer stack trace.
- **#10 simulation p-values** (`format_sim_pval()` in `perm_utils.R`): p = 0 is reported as the string `"< 1/reps"` (`< .01` for 100 reps, `< .001` for 1000, `< .0002` for 5000). jmvcore accepts a string in a number column, so the cell shows exactly that. Consequence for R users: `results_table(r)$p` is character in that case (tests use a `p_num()` helper).
- **#9 / #11 too few bars, line between stacks** (`choose_binning()`): for *densely occupied* lattices (proportions k/n: ≥ 60% of lattice points in the central 99% are achieved) the bin width starts at one lattice step whenever the full range fits in the target bin count (30 for ≥ 225 reps; grouped beyond that, so mean differences of rounded scores at 5000 reps get ~26 bars, not 52), so up to n ≈ 80 every achievable proportion gets its own bar / stack (n = 100 sits at the boundary and usually groups 2 steps per bar, as v0.2.0 did) and a simulation equal to the observed value stacks on the line. Honest tail gaps no longer force coarser bins; coarsening happens only for a sawtooth (mixed lattices) or an empty bin between two bins with ≥ 5 sims. Sparse lattices (chi-square) and continuous statistics keep the old gap-free ladder; the visual battery confirmed all 58 non-lattice renders are byte-identical.
- **#7 counts on bars** (`showCounts` option in every analysis, default off): `count_labels()` prints the count above each bar / dot stack (red for the shaded tail); `plot(r, show_counts = TRUE)` forces it from R. Every bar is labelled (all or none; the user turns the option off if they get too small). `count_label_size()` sizes labels to fit the widest count in one bar's share of Jamovi's 400 px plot width: as large as the tick labels (size 3.9 ≈ 11 pt) when they fit, shrinking to the size-3 floor, and vertical below that (again 3–3.9 by bar spacing). The plot state now also carries `domain`, so toggled plots from R keep the statistic's bounds.
- **Jamovi 2.7 formula sandbox (found while testing in the app; not in any issue)**: two-means test, two-means CI and the F test errored in Jamovi 2.7.38 — see "Important notes" below. Fixed by resampling without `infer` for those three. Seeded results for them differ from v0.2.0 (different RNG stream).
- **Found while testing, also fixed**: (a) chi-square from a 2×2 table (Yates-corrected, so values 0 and ≈0.08 nearly coincide) drew every bar as a sliver in one-bar-per-value mode — `sparse_groups()` now merges values closer than a quarter of the median gap into one column at their count-weighted mean, never across the observed value, and sparse mode admits up to 12 distinct values when they form a sparsely occupied lattice (`is_sparse_values()`, `lattice_info()`); (b) the model-based density for chi-square df ≤ 2 / F df₁ ≤ 2 spikes at zero and flattened the tail — the y axis is capped at 2.5× the density at the median so the curve runs off the top instead; a negative chi-square / F observed value draws its line at 0.

## Edge-case hardening (develop, 2026-09-30, second testing round)
An edge-case sweep (`scratchpad edge_sweep.R` pattern: every analysis on constant data, n = 1–3, reps = 1–5 and 20 000, boundary options, bad counts) found no crashes in normal use and sub-2-second runtimes at 10 000 reps, but a set of unclean failures on degenerate input, now fixed:
- **Clear messages instead of stack traces**: F test on constant data or one obs per group; slope tests with a constant predictor or < 3 rows (all via the analyses' existing footnote mechanism); single-mean CI with n = 1 (`reject`) — a constant sample now gets a point CI without going through `infer`'s `t.test()`; proportion counts that are missing, negative, fractional, both zero, or not exactly two rows.
- **Option bounds**: `reps` is now `Integer, min: 1` in every analysis (a fractional or zero rep count used to produce nonsense such as p "< .093"); `confLevel` is bounded to 1–99.9 everywhere (100 gave an infinite t multiplier / min-max "CI"). R users must pass `confLevel = 95`, not `0.95`.
- **Dot stacks rest on the axis**: dot k is centred at k − ½ (stack top edge = its count, where the count label sits) and the count axis never shows fewer than 8, so a short stack's bottom dot touches the baseline instead of hovering half a unit up.
- **Sparse mode needs structure**: one-column-per-value now requires a lattice or heavy repetition (`nu ≤ n/2`), not merely ≤ 8 distinct values; 5 continuous reps are binned (sizing dots by the smallest random gap made them near-invisible), while a Yates 2×2 chi-square (8 values, 300 reps, not a lattice) stays one column per value.
- **Cosmetics**: dot radius capped at 4 mm (1–3 reps drew dinner-plate dots); with ≤ 10 simulations or ≤ 2 columns the observed value is always on the axis rather than an edge arrow; chi-square/F densities with huge df start at the 0.05% quantile instead of 0 so the curve is not a spike; the two-proportion footnote distinguishes "not 2×2" from "2×2 with an empty row/column".
- `compute_null_pval()` muffles infer's "p-value of 0" warning (the table reports `< 1/reps`).
- Known, left alone: a Z of 10⁶ or F(1, 1) in the model-based calculator draws an unreadable spike (nonsense input); permutation tests on constant data show one all-red column at 0 with p = 1 (correct, just odd).

## Bug-hunt round 7: missing values (develop, 2026-10-01)
A missing-value battery (`na_battery.R` pattern: NAs in every variable of every analysis, padded columns, all-missing groups, 0–3 complete pairs) found five unclean paths, all fixed with regression tests under "Missing values" in `tests/test_analyses.R`:
- **"Values are counts" rejected a padded column** (regression from the edge-case round): jamovi pads shorter columns with blanks, so a 2-row count column beside longer data arrives as `c(12, 8, NA, NA, NA)`; the validator looked at the raw column and said "must hold exactly 2 counts (found 5 rows)". It now validates the blank-stripped values (the count extraction always did).
- **A missing count beside present row / column values** reached `chisq.test` as NA in all three table analyses ("all entries of 'x' must be nonnegative and finite"; jmv's own contingency table crashes the same way). Now a clear `reject`; rows whose row / column value is itself missing are still simply omitted.
- **A group whose values are all missing** (two-means test / CI): the level survives `droplevels()` (applied before the NA rows go), every resampled statistic was NaN and infer's `get_p_value()` threw. Now a footnote naming the group.
- **Fewer than 2 complete pairs** (paired test / CI): one pair reached `infer::specify()` → `t.test()` ("not enough 'x' observations"). Footnote.
- **Constant paired differences** (every post = pre + c, including pre == post): `infer::specify()` runs `t.test()` internally, which refuses them ("data are essentially constant"). The paired test now draws the sign-flip permutation directly in that case (`rowMeans` of random ±1 × c; matches the exact sign test) and the paired CI returns the point interval, as the single-mean CI already did.
- **Paired analyses only ever analysed the first pair** (on `main` too): the `Pairs` control lets a student add several pairs, the tables showed a blank row for each extra pair, and the single simulation plot belonged to the first. Both backends now loop over the pairs (one table row, one simulation plot and one descriptive plot per pair, like jamovi's own paired t-test): `simplot` is an `Array` keyed by `(pairs)` with an `Image` template, titled "i1 − i2"; descriptive row keys include both variable names so two pairs may share a variable. `plot(r)` (and the tests' `sim_img()` helper) return the first pair's plot. A one-pair cap via `maxItemCount: 1` is NOT an option: the compiler then reads the control as a single `Pair`, decides it no longer matches the `Pairs` option, and regenerates the whole `.u.yaml` (variable supplier moved to the bottom, `suggested`/`permitted`/`persistentItems` dropped) — restore the file from git if that ever happens.
- `format_sim_pval(0, 1)` printed "< 1." (trailing dot); now "< 1".
- The seed text box showed the default 8675309 truncated to "867530" in every panel; the `rngSeed` TextBox now has `width: large` in all 13 `.u.yaml` files (a property jmv uses; adding a property to an existing control does not trigger the compiler's regeneration). R sources are ASCII-only (`\u` escapes for the model-based notes).
- Not a module bug: `modelBased(obsStat = NULL)` from R dies in jmvcore's own option range check (`value > max` on NULL); jamovi always sends the box's number. Every analysis on a 0-row or all-blank sheet gives a clean message.
- **Reopening a file whose paired analysis was saved by an earlier build** (single `simplot` Image) under the Array definition: replicated jmvcore's `.load()` headlessly under Jamovi's R (`RProtoBuf::read(jamovi.coms.AnalysisResponse, raw)`, `options$compProtoBuf`, `results$fromProtoBuf`) — restores without error, and the re-run gives identical draws. Display-only toggles (counts, plot type, hypothesis, descriptives, confidence level, CI type) keep every pair's simulations; `reps` redraws.
- Verified clean: seeded results and bar counts are identical when the data are scaled by 10⁻⁹ … 10⁹ (lattice detection and snapping are relative); continuous 1000-rep histograms show 25–31 bars (31 when the anchoring at the observed value needs one partial bin at each end — `main` did the same, so not a regression; the 30-bar cap Brian signed off on is for the dense-lattice one-step-per-bar case); large typed-in counts scale (a 2×2 with 100 000 total at 1000 reps takes 4–8 s; 20 000 under 2 s); descriptives, observed statistic and test share the complete cases; NA factor rows drop out of the contingency tables; a 100 000-rep dotplot simulates in 0.7 s and renders in 0.4 s.

## Consistency round (develop, 2026-10-01)
- **Simulations survive display-only option changes** (`cached_sims()` in `perm_utils.R`): Jamovi re-runs `.run()` on every option change, so toggling counts / plot type / descriptives used to draw a fresh simulation and the plot changed shape for no reason. Each analysis now keeps its simulations in the results table's state keyed on everything that determines them (the data vectors actually used, reps, seed settings, test value / compare / table), and recomputes only when the key changes. Edited data changes the key, so a stale cache is impossible. Hypothesis direction still re-simulates (it is in the tables' `clearWith`, as before).
- **Bin count no longer a lottery**: `choose_binning()` judged gap-freeness on the full range first, so one stray tail simulation dropped a 1000-rep null from 30 bars to 16 or 13 on ~2 runs in 3 (measured: 9 to 31 bars across 30 runs). Occupancy is now judged on the central 98% (`try_ladder(0.01, 0.99)`) and, from 300 reps up, an empty bin only disqualifies a width when both nearest occupied neighbours hold ≥ 5 simulations (`gap_ok()`). Measured over 30 runs × {normal, χ²₃, t₂, F₃,₂₀} × {50…5000 reps}: the window alone still varied 16–30 bars at 300 reps and 20–30 for F/χ² at 1000; with the neighbour rule every ≥ 300-rep case lands on the target count (χ²₃ at 300: 24–30), and no run shows an empty bin inside the central 90%. Below 300 reps the strict rule stays (bar count may vary 5–20 but the plot is never gap-toothed; the alternative was body gaps in up to 40% of 100-rep F plots). `assert_gap_free` mirrors the rule; new invariants assert run-to-run stability for five distribution shapes.
- **Bars no longer depend on the alternative** (`bin_index()`): the half-resolution nudge that keeps lattice values off bin edges used to point in the tail direction, so with rounded data (bin width = m lattice steps) every m-th simulated value sat exactly on an edge and switched sides when the student switched "less" ↔ "greater" — the same cached simulations drew a visibly different histogram (24 of 28 bars changed in the test case). Assignment now uses one partition (nudge rightward) and relabels for a mirrored grid; only the tie column at the observed value moves with the direction, as it must (ties are shaded). Invariant test: rounded-data histograms for less / greater differ only in the two bars at the line, by exactly the tie count; continuous data identical.
- **Bin width never depends on the direction either** (`bin_counts()` inside `choose_binning()`): the occupancy window used to be taken as 1%/99% quantiles of the bin *indices*, which after mirroring the grid kept one more simulation on one side than the other; at 100 reps that single tail simulation decided whether a width was gap-free, so "less" and "greater" drew 7 vs 13 bars from identical simulations (90 of 200 samples). The window now trims a fixed count of simulations from each end of the sorted values, identical for both directions. Invariant: identical widths for less/greater over 60–1000 reps × 15 seeds, rounded and continuous.
- **One-value-per-bar histograms are value-centred** (proportions with n ≲ 80, differences in proportions with small groups): the value-at-edge convention made the tie bar jump to the other side of the line with the direction and, after the partition fix, merged the tie value with its lower neighbour for "less" (13 vs 12 bars). Single-value bars now sit centred on their value like the dot stacks; the tie bar straddles the line, shaded in either direction. Invariants judge single-value bars by centre and assert identical bars for less / greater / two-sided.
- **Floating-point ties** (`snap_stat()`): a simulated difference in proportions computed as 15/25 − 11/25 is one ulp below 0.16 and was counted on the wrong side of ≥; every comparison with the observed value (p-value, tail shading, tie column) now rounds both to 10 significant digits first. The real two-prop pipeline happened to produce exact ties, but the hazard was demonstrable.
- **`reps` capped at 100 000** (`max:` in every `.a.yaml`): simulations are now stored twice (plot state + cache), 1.6 MB at 100 000 reps; 250 000 would hit Jamovi's 4 MB message limit and spin forever.
- **Hidden (filtered-out) factor levels**: a jamovi filter leaves the unused levels on the factor. The two-means / F analyses already `droplevels`; now the proportion analyses drop unused levels beyond two (a 2-level factor with an empty level is still allowed, for the 5-heads-0-tails case), and the two-proportion and chi-square analyses compute on the table with empty rows / columns removed while the displayed contingency table keeps every level. A genuinely empty level of a 2-level factor still reports "empty row or column", not a silent drop.
- `cached_sims()` validates the cached object (data frame with a numeric `stat` column) before reusing it, so state written by an older build or corrupted in an `.omv` falls through to a recompute.
- Running the test suites under `Rscript` uses the C locale; non-ASCII level names (Café, ≥ 30) then fail inside jmvcore's note formatting with "'replacement' is invalid UTF-8". Under `LANG=en_US.UTF-8` (what jamovi's engine runs) they work; not a module bug.
- **Direction / confidence options no longer re-simulate**: `hypothesis`/`alt`, `confLevel`, `ciType` were in the cache tables' `clearWith`, so jamovi wiped the cached simulations when a student switched the alternative or the confidence level. Removed from the holders' `clearWith` (the plot and the numbers still update; only the draws are kept). A test parses every `.r.yaml` to keep those lists clean, and an option-change matrix test re-runs each of the 13 analyses in-process for every display/inference option (must keep the draws) and every simulation input (must redraw).

## Plot binning rework (fix/plot-quality branch)
Distribution plots previously produced histograms with irregular gaps/widths
(binwidth aliasing against discrete statistics) and dotplots with a crushed
x-axis (`coord_equal` vs tall stacks). Reworked in `R/binning_utils.R`:

- **Discreteness-aware, gap-free binwidth** (`choose_binning()`): detects when
  statistics lie on a lattice (proportions = k/n) — robust to one-ulp
  floating-point phantom duplicates — and snaps binwidth to an integer multiple
  of the lattice spacing. Zero interior empty bins by default (two passes: the
  first demands gap-free occupancy over the full range; only a genuinely
  detached outlier falls back to a windowed pass and keeps its own bar with
  honest empty space). Target bin count scales with rep count (~2*sqrt(n), max 30).
  Dense lattices are exempt from the gap rule at one step per bin (see the
  issue-fix section above).
- **Pedagogical invariant enforced by construction**: bins are anchored with an
  edge exactly at the observed statistic, and each simulation's extreme flag
  (the same `>=`/`<=` comparison as the p-value) clamps it to its own side, so
  no bar or dot stack ever mixes extreme/non-extreme values — stacks are always
  a single color.
- **Dots are always true circles** (`GeomDotStack` drawing at grid makeContent
  time from the real panel geometry, re-run on every resize): a circle whenever
  it fits under the no-overlap cap, coin-stack overlap with a legible radius
  floor for very tall stacks. Replaced ggforce ellipses (ggforce dependency
  dropped entirely).
- **Ties stack on the observed-value line**: when each column represents exactly
  one achievable value (binwidth = lattice spacing), dot columns sit at their
  exact values. Grouped bins keep midpoint placement (centering the grid on the
  observed value there would put a mixed-color stack under the line).
- **Sparse statistics (2–8 distinct values**, e.g. chi-square from a 2x2 table,
  or a handful of reps): one value-centered bar / dot column per achievable
  value; the space between values is honest, not a binning artifact.
- **Domain bounds**: chi-square/F pass `domain = c(0, Inf)`, single proportion
  `c(0, 1)`, two-proportion difference `c(-1, 1)`; grouped bars are trimmed,
  grouped dot-column centers clamp to the bound, bootstrap bars trim to the CI
  clamp bounds. Nothing is drawn at impossible values (single-value bars keep
  the value-at-edge convention and may extend one lattice step past a bound).
- Bootstrap CI lines are drawn at the exact reported bounds — a dashed line
  falling inside a bar is fine (CI plots shade no tail), and truthful.
- Bare/no-text toggle modes draw bars at identical positions to the full plot
  (verified by tests), so "estimate then reveal" slide sequences line up.
